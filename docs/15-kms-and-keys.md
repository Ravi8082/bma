# KMS and key management

**Production:** AWS KMS (or GCP Cloud KMS / Azure Key Vault, chosen per deployment region).
Envelope encryption: the data key is generated by the application, wrapped by KMS, and stored
alongside the ciphertext as `key_version`. Rotation re-wraps the data key without re-encrypting
the data.

**Local dev:** A 32-byte key is read from `FIELD_ENCRYPTION_KEY_REF` (default `dev-local-kms-key`
in `.env.example`). In production, this ref must be a KMS key ARN/URI, not a raw key. The
application refuses to start in production if the ref does not look like a KMS reference.

**Blind index key:** `PHONE_BLIND_INDEX_KEY` — in production this comes from the secret manager
(AWS Secrets Manager / GCP Secret Manager). In dev it is a default string. Never stored in the
database.

**OTP pepper:** `OTP_PEPPER` — same source as the blind index key.

**No key lives in `.env` or the database in production.** The `.env` file contains only
references (ARNs/URIs) to secrets in the secret manager. The database stores only ciphertext,
blind indexes, and `key_version` integers. A catalog query (`DB-44`) asserts that no column in
the `app` schema contains key material.
